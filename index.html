Module 1

Blockchain basics

A blockchain is a shared record book that no single person controls. Before diving into the cryptography, let’s understand the problem it solves.

The problem: trusting a record keeper

Banks, land registries and payment networks all work the same way: one trusted party keeps the official record. That works — until the record keeper makes a mistake, gets hacked, censors you, or simply isn’t trusted by everyone involved.

A blockchain flips the model: everyone keeps a full copy of the ledger, new entries are only added when the network agrees on them, and old entries are mathematically protected from editing.

Four properties to remember

Distributed
Thousands of computers (nodes) each hold the complete ledger.
Append-only
You can add new records, but never edit or delete old ones.
Tamper-evident
If anyone alters history, every other copy immediately exposes the change.
Consensus-driven
Rules — not a boss — decide which new entries are accepted.

Try it: who decides the truth?

Five nodes hold identical copies of a tiny ledger. Mallory wants the last entry to read “Carol → Mallory: 99”. Let her corrupt one node, then another, then another — and watch what the network as a whole believes.

One forged copy changes nothing: the others still agree, so the network ignores it. But notice the catch at three. If votes were counted per computer, Mallory wouldn’t bother hacking nodes — she’d spin up a million fake ones for free (a Sybil attack). So real blockchains weight each vote by something scarce: computing work in proof of work (Module 4) or locked-up coins in proof of stake (Module 6). A “51% attack” means controlling a majority of that.

Where does cryptocurrency fit in?

A cryptocurrency is simply what the ledger tracks: entries like “Alice pays Bob 5 coins”. Because the ledger can’t be forged or rewritten, those entries behave like money — scarce, transferable, and not dependent on any bank. Bitcoin (2009) was the first system to make this work; thousands of others followed.

Try it: do you actually need a blockchain?

Decentralization is bought, not free. Every node stores and re-checks everything, so a public blockchain is a spectacularly slow database: Bitcoin settles ~7 transactions per second and Ethereum ~15–30, while one ordinary database server handles tens of thousands. Pick a scenario — or answer the three questions yourself.

The three-question test

A blockchain earns its cost only when all three hold. Most “enterprise blockchain” projects of the 2010s quietly became shared databases for exactly this reason: the participants already had a referee.

Key takeaways

  • A blockchain is a shared, append-only ledger that many independent nodes keep in sync — there is no single record keeper to trust or attack.
  • Editing your own copy achieves nothing while the honest majority disagrees; history changes only if an attacker controls the majority.
  • Votes must be weighted by something costly — work or stake — because counting computers invites Sybil attacks.
  • Decentralization costs speed and money. It pays off only with many mutually distrustful writers and no acceptable middleman.

Forty years of failed digital cash — then Bitcoin

Digital money is an old dream with one stubborn bug: a digital coin is just data, and data can be copied. Every attempt before Bitcoin patched the copying problem the same way — put one trusted company in charge — which simply recreated a bank.

  • 1982 — Lamport, Shostak & Pease formalize the Byzantine generals problem: how can independent parties agree when some of them may lie? Every blockchain is an answer to this question.
  • 1989 — David Chaum’s DigiCash issues cryptographic e-cash — run by a company, which went bankrupt in 1998. Centralization was the single point of failure.
  • 1997 — Adam Back’s hashcash makes email senders burn CPU time to deter spam: proof of work is born (you’ll meet it in Module 4).
  • 1998 — Wei Dai’s b-money and Nick Szabo’s bit gold sketch decentralized money, but neither has a working consensus mechanism.
  • October 2008 — the pseudonymous Satoshi Nakamoto publishes a nine-page whitepaper wiring all of these pieces together.
  • 3 January 2009 — the Bitcoin genesis block is mined, with a newspaper headline embedded in it forever: “Chancellor on brink of second bailout for banks.”

Notice what Bitcoin didn’t invent: hashes, signatures and proof of work all existed. The breakthrough — now called Nakamoto consensus — was wiring them together so that thousands of strangers converge on one history with nobody in charge.

The blockchain trilemma

Three properties everyone wants — and a base layer realistically maximizes two:

Decentralized
Anyone can run a node and verify the rules — no gatekeepers.
Secure
Rewriting history or censoring users is economically irrational.
Scalable
High throughput, low fees, fast confirmation.

The trade-offs are mechanical, not accidental: bigger or faster blocks mean fewer people can afford to run a node (less decentralized); a small hand-picked validator set is fast but reintroduces trust. Bitcoin and Ethereum deliberately sacrifice base-layer speed, then push scale to layer 2 networks that inherit their security — Module 7 shows how.

Module 2

Hashing — the fingerprint machine

Every security promise a blockchain makes traces back to one tool: the cryptographic hash function. Master this and the rest of the course clicks into place.

What a hash function does

A hash function takes any input — a letter, a novel, a 4 GB movie — and produces a fixed-size fingerprint. Bitcoin and this course use SHA-256, which always outputs 256 bits (written as 64 hex characters).

  • Deterministic — same input, same hash. Always.
  • One-way — there is no way to compute the input from the hash. Guessing is the only option.
  • Avalanche effect — change one character and the entire hash changes beyond recognition.
  • Collision-resistant — finding two inputs with the same hash is astronomically hard.

Why blockchains care

Blockchains use hashes as tamper-evident seals. Hash a block’s contents and you get its fingerprint; change anything inside the block and the fingerprint no longer matches. In the next module you’ll see how chaining these fingerprints together protects an entire history.

Scaling up: Merkle trees

A real block holds thousands of transactions, but it doesn’t store one giant hash of everything. Instead it hashes transactions in pairs, then hashes those hashes in pairs, and so on, up to a single fingerprint-of-fingerprints: the Merkle root. The root goes in the block header, so the header commits to every transaction beneath it — and, as you’re about to see, proving one transaction is in the block takes only a handful of hashes.

    How hard is a hash to break?

    “Breaking” a hash means one of two very different things. A preimage attack starts from a given hash and hunts for an input that produces it — like forging a block that matches an existing fingerprint. A collision attack just hunts for any two inputs with the same hash. The second sounds only slightly easier. It is enormously easier — the same maths that makes it likely two people in a room of 23 share a birthday.

    We can’t attack all 256 bits of SHA-256 (nobody can), but we can attack the first few. Demand that only the first N bits match and both hunts become feasible — and you can watch how differently they scale.

    Hashes as sealed envelopes

    Because a hash is one-way and collision-resistant, publishing one is like posting a sealed envelope: you can commit to a value today and open it later, and nobody — including you — can swap the contents in between. Commitments power sealed-bid auctions, fair coin flips between strangers, and the zero-knowledge proofs of Module 10. There’s one catch, and it’s worth breaking on purpose.

    Key takeaways

    • A hash is a fixed-size fingerprint: deterministic, one-way, and wildly sensitive to the smallest change.
    • A Merkle tree folds a block’s transactions into one root; proving one is included takes only ~log₂(n) hashes.
    • Collisions take roughly the square root of the work of preimages, so a 256-bit hash gives 128-bit collision security.
    • Hash + random salt = a commitment: binding (can’t be changed) and hiding (can’t be guessed).

    How big is 2²⁵⁶, really?

    SHA-256 has 2²⁵⁶ possible outputs — about 1.2 × 10⁷⁷, within a few zeros of the number of atoms in the observable universe (~10⁸⁰). Intuition fails at this scale, so try arithmetic instead: give a billion computers a billion guesses per second each. That’s 10¹⁸ guesses per second, or ~3 × 10²⁵ per year — meaning covering even half the output space would take around 10⁵¹ years, roughly 10⁴¹ times the age of the universe.

    This is why “brute-force it with a bigger computer” isn’t a threat. The bound is physical, not merely technological: just counting through 2²⁵⁶ states has a minimum thermodynamic energy cost (Landauer’s principle) far beyond the Sun’s total output. When hash functions do fall, they fall to math — a clever shortcut — not to muscle. See the next deep dive.

    SHA-256’s family tree — and why old hashes get retired

    SHA-256 (published 2001, part of the SHA-2 family) pushes input through 64 rounds of public, keyless bit-mixing; its security rests entirely on nobody finding structure in that mixing. Its predecessors did fall: MD5 collisions now take seconds, and SHA-1 fell in 2017 when researchers published two different PDFs with the same hash. Both falls were algorithmic breakthroughs, not bigger computers — which is why the industry retires hash functions at the first crack.

    Variations you’ll meet in the wild:

    • Bitcoin applies SHA-256 twice (“SHA-256d”) when hashing blocks.
    • Ethereum uses Keccak-256 from the SHA-3 family — different internals, same fingerprint contract.
    • Addresses often layer hashes: Bitcoin runs RIPEMD-160 on top of SHA-256 (Module 5).

    None of this is magic you have to take on faith. The miner and the collision hunt on this site run a plain-JavaScript SHA-256 of about a hundred lines — 64 rounds of shifts, rotations, additions and XORs — in js/lib/sha256.js, which the project’s tests check bit-for-bit against a standard implementation.

    Hashes beyond blockchains
    • Git — every commit ID is a hash of the code plus its history; change anything and the ID changes. A repository is itself a small Merkle structure.
    • Passwords — sites store hash(password), never the password. There they use deliberately slow hashes (bcrypt, Argon2) to blunt guessing — the exact opposite of mining’s speed race.
    • Downloads & packages — published checksums let you verify a file wasn’t corrupted or tampered with in transit.
    • Deduplication & BitTorrent — identify content by what it is rather than where it lives (“content addressing”).
    The three resistances — and why birthdays matter

    “One-way” is really three separate promises. Preimage resistance: given a hash, you can’t find any input that produces it. Second-preimage resistance: given one input, you can’t find a different input with the same hash. Collision resistance: you can’t find any two inputs that collide at all — the weakest of the three, as the hunt above showed. The reason is counting pairs: after k tries a preimage hunt has made k comparisons against its one target, but a collision hunt has made k(k−1)/2 — every new hash is compared with every old one. Pairs grow with the square of the effort, so a collision turns up after about √(2N) tries. That’s why output size and security level are not the same number: SHA-256 offers 256-bit preimage but 128-bit collision security.

    There’s a second subtle edge. SHA-256 digests a message by streaming it through an internal state (the Merkle–Damgård construction) and then publishes that final state as the hash — which lets an attacker who knows the hash of secret + message compute the hash of secret + message + anything without knowing the secret. That’s the length-extension attack, and guarding against it is the usual explanation for why Bitcoin hashes block headers twice (“SHA-256d” — SHA-256 of SHA-256): the second pass hides the internal state. (Satoshi never stated the reason; double hashing was a common defensive recommendation at the time.) Keccak/SHA-3, which Ethereum uses, is immune by design. None of this threatens mining; it’s why protocol designers reach for the right hash construction, not merely the right number of bits.

    A blockchain is literally a chain of blocks — and the links are hashes. Time to break one on purpose.

      • Each block stores the previous block’s hash, so editing any block breaks every block after it.
      • Repairing a broken chain means redoing the proof of work for every later block — faster than the honest network.
      • A real Bitcoin block hash is SHA-256 applied twice to an 80-byte header; transactions are covered through the Merkle root.
      • A block is valid when its hash, read as a number, is below the target encoded in the header’s “bits”.

      Transactions live in the block body; only this 80-byte header is hashed during mining, which is why mining speed doesn’t depend on how full a block is. And because a 4-byte nonce allows only ~4.3 billion guesses — an ASIC exhausts that in well under a second — miners also tweak the timestamp, an extraNonce inside the first transaction (which changes the Merkle root and opens up a fresh 4.3 billion), and spare bits of the version field (“version rolling” — hence block 840,000’s odd version).

      One more trick: the nonce sits in the header’s last 16 bytes, and SHA-256 digests input in 64-byte chunks. So miners hash the first 64 bytes once — the “midstate” — and redo only the final chunk for each new nonce. The re-mining demo above does exactly that.

      Ties, orphans and the longest-chain rule

      Every so often two miners find valid blocks within seconds of each other. Both are valid; nodes near miner A hear A’s block first, nodes near B hear B’s. The tie isn’t debated — it’s raced: whichever branch receives the next block becomes the longer chain, and every node hops onto it. The losing block is orphaned (“stale”): its mining reward evaporates and its transactions return to the mempool to be confirmed again.

      Two practical consequences. First, “longest” really means most accumulated work — a million easy blocks don’t outrank ten hard ones. Second, this is exactly why recipients wait for confirmations: a transaction one block deep can still land on the losing side of a tie, but each further block makes reversal exponentially less likely — hence the ~6-confirmation custom for large Bitcoin payments.

      How heavy is the chain?

      A Bitcoin block carries roughly 2,000–4,000 transactions every ~10 minutes, and the full chain since 2009 runs to hundreds of gigabytes — Ethereum’s state is heavier still. The ecosystem copes in three tiers: full nodes verify everything (the gold standard); pruned nodes verify everything but discard old block bodies, keeping headers and current balances; and light clients download just the 80-byte headers and check individual transactions with Merkle proofs (Module 2). The design fights hard to keep at least light verification cheap — if ordinary people can’t verify the chain, decentralization is a slogan.

      Module 4

      Mining & proof of work

      Mining sounds mysterious, but you just did it in Module 3. It’s a guessing game — played at planetary scale.

      The lottery puzzle

      To add a block, a miner must find a nonce that makes the block’s hash start with a required number of zeros. Hashes are unpredictable, so there’s no shortcut: miners simply try nonce 0, 1, 2, 3… billions of times per second. Finding a winning nonce is hard; checking it takes anyone a single hash. That asymmetry is the magic.

      • Difficulty — each extra required zero multiplies the expected work by 16 (in hex). Networks auto-tune difficulty to keep block times steady.
      • Reward — the winning miner earns new coins plus fees. This is how new cryptocurrency enters circulation.
      • Security — rewriting history means redoing all that work and outpacing every honest miner. The energy cost is the lock on the vault.

      The difficulty thermostat

      If mining is a lottery, what stops blocks from arriving faster as more miners join? Every 2,016 blocks (about two weeks) every node measures how long those blocks actually took. Faster than ten minutes each → difficulty rises in proportion; slower → it falls, never by more than 4× at once. Hashpower has grown by a factor of trillions since 2009, yet blocks keep their ten-minute heartbeat and coins are issued no faster. Extra hashpower only buys miners a bigger share of the same rewards — and makes the network more expensive to attack.

      Built-in scarcity: the halving

      Mining doubles as Bitcoin’s mint: the block reward is the only way new coins are ever created. And the mint runs on a countdown — every 210,000 blocks (roughly four years) the reward halves: 50 BTC at launch, 25 from 2012, 12.5 from 2016, and so on. The halvings turn issuance into a geometric series whose sum stops just short of 21 million BTC, with the last fraction of a coin mined around the year 2140.

      • Mining is a guessing game: find a nonce whose hash falls below the target. Finding takes trillions of guesses; checking takes one.

      From laptop CPUs to warehouse ASICs — and pools

      Mining hardware escalated in four waves: CPUs (2009, Satoshi and a handful of hobbyists), GPUs (2010, ~100× faster at parallel hashing), FPGAs (2011, briefly), then ASICs (2013 on) — chips that can do nothing except SHA-256, but do it millions of times faster per watt than a CPU, and are obsolete within a couple of years. Solo mining became a lottery ticket with terrible odds, so miners formed pools: thousands combine hashpower and split each reward in proportion to work contributed, trading jackpot odds for a steady trickle.

      Pools create a real centralization tension: the pool operator chooses which transactions go in the blocks, and a handful of large pools often add up to more than half the network. The counterweight is that pool members can switch pools in minutes — operators who misbehave bleed hashpower — but it’s a live debate, not a solved problem.

      The energy question, honestly

      Proof-of-work security is energy — that’s the design, not a side effect. Estimates put Bitcoin around 100–150 TWh per year, roughly half a percent of world electricity, comparable to a mid-size country. Defenders point out that miners chase the cheapest power and so soak up stranded hydro, flared gas and off-peak surplus; critics answer that the footprint scales with the coin’s price, not its usefulness, and that ASIC churn adds e-waste.

      One engineering fact both sides accept: proof of stake delivers comparable security guarantees from economic collateral instead of electricity — Ethereum’s 2022 switch (“the Merge”) cut its energy use by ~99.95%. Bitcoin keeps proof of work deliberately: its community regards a security budget rooted in physics, outside the system itself, as worth the cost. That disagreement — physical cost versus financial collateral — is the real content of the energy debate, and Module 6 compares the two models head-on.

      Reading the target: what “difficulty” is, in numbers

      Our demo asks for leading zeros, but Bitcoin’s real rule is subtler: a block is valid when its header hash, read as one gigantic 256-bit number, is less than or equal to a target. Leading zeros are just the visible side-effect of a very small target. The 80-byte header (Module 3) packs that target into a 4-byte field called bits — a compact floating-point-like encoding, one byte of exponent and three of mantissa — and every node expands it the same way to check the winner. Difficulty is then simply a ratio: the easiest-ever target divided by the current one. “Difficulty 1” was the genesis setting; block 840,000 (April 2024) sat at about 86 trillion, and the figure has since climbed past 100 trillion.

      That ratio has a beautifully concrete meaning — the expected number of hashes to mine one block is difficulty × 2³². At a difficulty around 100 trillion that’s roughly 4 × 10²³ hashes per block (hundreds of zettahashes), network-wide, every ten minutes. It also explains the 4-byte nonce problem from Module 3: 2³² ≈ 4.3 billion guesses is a rounding error against 10²³, which is why a miner exhausts the nonce in well under a second and must keep varying the coinbase and timestamp to refresh the search space. Difficulty isn’t a vague knob — it’s an exact, auditable number that every node recomputes and enforces.

      Keys, wallets & signatures

      If hashes protect the history, digital signatures protect the ownership. Your “account” on a blockchain is nothing more than a key pair.

      The key pair

      • Private key — a giant random number only you know. It is your identity. Whoever holds it controls the funds — there is no “forgot password” link.
      • Public key — derived from the private key and safe to share. Your address is (roughly) a hash of it.
      • Signature — a proof, computed with your private key, that you approved a specific message. Anyone can verify it with your public key; nobody can forge it without your private key.

      A wallet doesn’t hold coins — coins only exist as ledger entries. A wallet holds your keys and signs transactions on your behalf.

      From public key to address

      An address is not the public key — it’s a hash of it, shortened and wrapped in a format with a built-in checksum. Bitcoin and Ethereum use the same curve, so one private key controls an address on each chain; only the hashing and the encoding differ.

        Typo test

        Why hash at all? It’s shorter, and a Bitcoin address keeps the public key itself off-chain until the first time you spend. The checksums are one of the few mercies in this system: a typo gets your payment rejected instead of sent into the void. Ethereum’s mixed-case checksum (EIP-55) arrived later and is optional — an all-lowercase address carries no protection at all.

        Seed phrases: one secret, endless keys

        Nobody should hand-copy a 256-bit number, so wallets encode their master randomness as 12 or 24 words from a fixed list of 2,048 (the BIP-39 standard). From that one seed, a hierarchical deterministic wallet (BIP-32) derives an unlimited tree of key pairs along standard paths — a fresh address per payment, on any chain. Restore the words on a new device and every key reappears.

          The signing nonce: one number that must never repeat

          Every ECDSA signature mixes in a fresh secret number k — confusingly also called a “nonce”, and a different one from mining’s. The signature is r = (k × G).x and s = k⁻¹(z + r·d), where z is the message hash and d the private key. Reuse k for two different messages and the private key falls out with schoolbook algebra. This isn’t hypothetical: Sony signed PlayStation 3 software with a constant k (exposed in 2010), and in 2013 a flawed Android random-number generator repeated k in Bitcoin wallets, which thieves promptly emptied.

          How the wallet picks k

            The fix is to stop rolling dice altogether. RFC 6979 derives k from the private key and the message itself, so it is unpredictable to outsiders yet can never accidentally repeat for two different messages — and signing the same message twice just reproduces the same signature, which leaks nothing. (Real wallets also apply “low-s” normalization; it’s omitted here to keep the algebra textbook.)

            Custody in one sentence

            “Not your keys, not your coins” — if an exchange holds your private keys, you hold an IOU, not cryptocurrency. Hardware wallets and seed phrases exist purely to keep private keys safe and recoverable.

            Key takeaways

            • A private key is a random number; the public key is that many hops along an elliptic curve — easy forward, infeasible backward.
            • An address is a hash of the public key in a checksummed format; one key yields addresses on many chains.
            • A seed phrase encodes the wallet’s master secret; the phrase is the wallet, so anyone who reads it owns everything.
            • Signatures prove approval of one exact message — and leak the key if a signing nonce is ever reused.

            What a “hop” really is: point addition

            Picture the curve over ordinary real numbers: a smooth loop-and-tail shape. To add two points P and Q, draw the straight line through them; it always crosses the curve at exactly one more point. Reflect that third point across the x-axis — that’s P + Q. Adding a point to itself uses the tangent line instead (“doubling”). It sounds arbitrary, but it obeys the familiar rules of addition, so k × G is well-defined however you group the hops.

            Over a finite field the same rule becomes pure arithmetic, every step taken modulo p: the slope is λ = (y₂ − y₁) / (x₂ − x₁) (division meaning multiplication by a modular inverse), then x₃ = λ² − x₁ − x₂ and y₃ = λ(x₁ − x₃) − y₁. The tiny curve above and the real secp256k1 code behind the address demo (js/lib/secp256k1.js) run exactly these formulas — the only difference is a 97 versus a 78-digit prime.

            Beyond ECDSA: Schnorr, multisig and the quantum question

            Bitcoin’s newer Schnorr signatures (activated with Taproot in 2021) keep the same curve but use a cleaner, linear equation. One big consequence: several keys can combine into one joint signature that looks exactly like a single person’s — cheaper multisig wallets, and more privacy.

            One honest caveat about all of this: a large-scale quantum computer running Shor’s algorithm would break both secp256k1 and P-256 (the sibling curve your browser’s Web Crypto uses in the signing demo above). Post-quantum signature schemes already exist and chains can migrate to them; it’s a watched-but-distant problem, and coins marketed today as “quantum-proof” are mostly marketing.

            How coins actually get stolen

            Essentially never by breaking the cryptography — the math holds. Real losses come from the seams around it:

            • Phishing — fake wallet sites, fake airdrops, “support” DMs asking for your seed phrase.
            • Malware — clipboard swappers that silently replace the address you just copied with the thief’s.
            • SIM swaps — hijacking your phone number to defeat SMS-based logins at exchanges.
            • Malicious approvals — signing a contract interaction that lets someone else move your tokens (Module 8 shows how).
            • Weak randomness — guessable keys and repeated signing nonces, as the demos above showed.
            • Custodial failure — exchanges collapsing with customer funds (Mt. Gox 2014, FTX 2022): the “not your keys” lesson, at scale.

            The defenses are unglamorous: a hardware wallet for savings, verifying addresses character-by-character (or via a second channel), keeping the seed offline, and assuming any request for it is a scam — because it is.

            Module 6

            Transactions & consensus

            You now know every ingredient. Let’s follow a transaction end to end, then look at the two big ways networks agree on the next block.

            Life of a transaction

            1. Create — your wallet drafts “Alice pays Bob 5”, referencing coins you own.
            2. Sign — your private key signs it (Module 5).
            3. Broadcast — it spreads node-to-node into the mempool, the waiting room of unconfirmed transactions.
            4. Confirm — a miner/validator packs it into a block (Modules 3–4). Each later block buries it deeper; ~6 confirmations is considered settled on Bitcoin.

            Consensus rules also solve the double-spend problem: if you broadcast two transactions spending the same coin, the network will only ever confirm one — the other is rejected as invalid.

            Coins, change and fees: the UTXO model

            Bitcoin stores no account balances anywhere. It tracks UTXOs — unspent transaction outputs — which behave like banknotes: a transaction consumes whole notes as inputs and creates new notes as outputs. To pay 0.25 BTC with a 0.2 and a 0.12 note, you hand over both; the transaction creates 0.25 for Bob and about 0.07 of change back to you. Anything you don’t assign to an output is the miner’s fee. Your wallet’s “balance” is just the sum of the notes you can spend.

                Beyond currency

                Once a network can agree on arbitrary data, it can agree on code. Smart contracts are programs stored on-chain that execute exactly as written — powering tokens, decentralized exchanges, lending markets (DeFi) and NFTs. Different goals, same foundations you just learned — and exactly where Module 7 goes next.

                Key takeaways

                • Bitcoin tracks unspent outputs, not balances: transactions consume whole coins and create new ones, including change; the leftover is the fee.
                • Block space is scarce, so miners pick transactions by fee rate (sats per vByte), not by total fee.
                • Reversal risk falls exponentially with each confirmation — unless the attacker controls a majority, in which case no wait is safe.
                • Proof of stake picks proposers in proportion to stake and slashes provable cheating, replacing energy with collateral.

                UTXOs vs accounts: Ethereum’s different bookkeeping

                The UTXO demo above is Bitcoin’s way. Ethereum instead keeps an account model: real balances, debited and credited, plus a per-account counter (the nonce — same word as mining’s nonce, different job) that orders your transactions and blocks replays. The trade-offs: UTXOs parallelize well and make coin-tracing slightly harder; accounts are far simpler for smart contracts, which need persistent state — you wouldn’t want to rebuild a token’s balance table out of bills on every call.

                Soft forks, hard forks and chain splits

                Who decides the rules of a system with no boss? Rule changes come in two flavors. A soft fork tightens the rules: blocks valid under the new rules are still valid under the old, so un-upgraded nodes keep following along (Bitcoin’s SegWit 2017 and Taproot 2021 shipped this way). A hard fork changes rules incompatibly: old nodes reject the new blocks, and if part of the community keeps mining the old rules, the network splits into two chains, each carrying the full shared history — which is why holders of pre-fork coins end up with coins on both.

                The famous splits were governance disputes settled by exit: Bitcoin Cash left Bitcoin in 2017 over block sizes, and Ethereum Classic is the chain that refused the 2016 DAO bailout fork (the full story is a Module 7 deep dive). Forks are blockchain politics: when consensus about the rules fails, the ledger itself divides.

                How final is “final”?

                Proof-of-work finality is only ever probabilistic: every confirmation buries your transaction deeper and makes reversal exponentially costlier, but the probability never hits zero. On giant networks that’s academic; on small ones it isn’t — Ethereum Classic and Bitcoin Gold both suffered real 51% double-spend attacks (2018–2020) because enough hashpower to overwhelm them could be rented by the hour. Security budgets matter.

                Ethereum’s proof of stake adds explicit checkpoints: validators vote on recent history, and once two-thirds of all staked ETH attests, the checkpoint is finalized (~13 minutes). Reverting a finalized block isn’t “very expensive” — the protocol guarantees it would destroy at least one-third of all staked ETH, tens of billions of dollars burned. The attack cost shifts from out-computing the network to incinerating your own capital.

                Beyond PoW and PoS

                Consensus is a design space, and every point in it is a different answer to Module 1’s trilemma:

                • Delegated PoS — coin holders elect a small validator set (EOS, Tron). Fast and cheap; visibly more centralized.
                • BFT committees — a bounded validator set votes on every block (Tendermint/Cosmos). Instant, clean finality; the validator list is the trust assumption.
                • Proof of authority — named, legally identifiable validators. Fine for testnets and consortium chains; not trustless at all.
                • Hybrids — e.g. Solana pairs PoS with “proof of history”, a cryptographic clock that lets validators order events without waiting on each other, buying huge throughput at the cost of heavyweight hardware requirements.
                MEV: who really decides the order

                The fee-market demo assumed a miner just sorts by fee rate. In reality the order of transactions inside a block is itself worth money, and whoever builds the block can reorder, insert or drop transactions to capture it. This is MEV — maximal extractable value. The classic move is a sandwich attack: a bot spots your pending swap on a decentralized exchange, buys just ahead of you (pushing the price up), lets your trade execute at the worse price, then sells right after — pocketing the spread, all inside one block. Cross-exchange arbitrage and racing to liquidate undercollateralized loans are gentler, often useful versions of the same thing.

                MEV reframes the mempool: it isn’t a fair queue, it’s a public auction room where “searchers” run bots and bid priority fees for favorable positioning (the Flashbots project built the first open marketplace for it). Left unchecked it pushes toward centralization — whoever has the best ordering algorithm earns the most and can outbid everyone for block space. Ethereum’s mitigation is proposer–builder separation: specialized builders compete to assemble the most valuable block and the validator simply picks the highest-paying one, so an ordinary validator doesn’t need a bot farm to keep up. It works, yet it concentrates power in a few dominant builders — an unsolved tension and one of the field’s most active research fronts. Extracted MEV is estimated in the billions of dollars since 2020.

                Gas: paying the world computer

                Running code on thousands of machines isn’t free. Every EVM operation has a fixed price in gas, and you pay gas used × gas price, in ETH. Gas does two jobs: it pays validators for computation and storage, and it makes runaway programs impossible — a program that runs out of fuel simply stops, and its transaction reverts.

                • Gas used — depends on the work: a plain ETH transfer is exactly 21,000 gas; contract calls add the cost of every operation they run.
                • Gas price — quoted in gwei (a billionth of an ETH): a base fee set by the protocol plus a tip you choose (the fee market below).
                • Layer 2 rollups — networks that batch thousands of transactions off-chain and post the result to Ethereum, cutting fees 10–100× (see “Rollups” below).

          Oracles: how contracts learn about the world
          
                      
            The EVM is deterministic and sealed: a contract cannot fetch a URL, because thousands of nodes would
            get different answers at different times and consensus would shatter. Any off-chain fact — a price,
            a match result, the weather — must be written in by a transaction. The service doing the
            writing is an oracle, and it quietly reintroduces trust: your trustless contract is
            exactly as honest as its data feed. This is the oracle problem.
          
                      
          
                      
            The standard mitigation is decentralizing the messenger — networks like Chainlink aggregate many
            independent operators and data sources, with staked collateral to slash liars. It works well enough
            to carry billions, but oracle manipulation (often pumping a thin market with a flash loan so a lending
            contract mis-prices collateral) remains one of the largest categories of DeFi exploit. When you
            evaluate any DeFi protocol, the first question is: where does its price come from?
          
                      
        
                      
        
                      
          Stablecoins: the dollar, tokenized
          
                      
            The most-used tokens aren’t volatile coins — they’re stablecoins, engineered to track
            the dollar. Three designs, three trust models:
          
                      
          
                        
            
                      • Fiat-backed (USDC, USDT) — a company holds dollars and T-bills, and mints one token per dollar. Simple and dominant, but custodial: you’re trusting the issuer’s reserves, and the issuer can freeze addresses.
                        • 
            
                      • Overcollateralized crypto (DAI) — lock ~$150+ of ETH in a contract to mint $100 of stablecoin; automatic liquidations keep the system solvent. Trustless-ish, capital-inefficient.
                        • 
            
                      • Algorithmic — peg maintained by mint-and-burn incentives with no full collateral. Terra/UST collapsed this way in May 2022, erasing ~$40B in days. Treat the category as a cautionary tale.
                        • 
          
                      
          
                      
            Stablecoins are arguably crypto’s most adopted product: most on-chain trading is denominated in them,
            and they move serious remittance volume. They’re also where blockchains and bank regulators meet.
          
                      
        
                      
        
                      
          Rollups, properly: optimistic vs ZK
          
                      
            Both kinds of layer 2 execute transactions off-chain and post compressed data back to Ethereum; they
            differ in how Ethereum knows the results are honest. Optimistic rollups (Arbitrum,
            Optimism, Base) assume batches are valid and give challengers ~7 days to submit a fraud proof
            showing a bad state transition — secure, but native withdrawals wait out the window.
            ZK rollups (zkSync, Starknet, Scroll) submit a validity proof — a succinct
            cryptographic certificate that the batch was executed correctly — which an L1 contract verifies in
            milliseconds before accepting; no challenge window, at the cost of much heavier math to generate.
          
                      
          
                      
            Either way the rollup inherits Ethereum’s security rather than bootstrapping its own — that’s the
            trilemma answer promised in Module 1. The economics improved sharply in March 2024 when EIP-4844 gave
            rollups “blobs”: cheap, short-lived data space on L1 that dropped typical L2 fees to cents. The
            roadmap bet is that users live on L2s while Ethereum’s base layer becomes the settlement court.

                      Module 8
                      
        
                      NFTs & digital ownership
                      
        
                      
          Module 7’s token kept a table of balances. Change that table to track
          unique items instead of amounts and you get an NFT — a deed, not a dollar.
        
                      

        
                      Fungible vs. non-fungible
                      
        
                      
          Most money is fungible: any one dollar — or BTC, or LAB token from Module 7 — is
          interchangeable with any other. You care about the amount, not which one. A
          non-fungible token flips that: every token is a distinct, indivisible item with its
          own ID and its own owner. You never hold “0.5 of token #7” — you either own #7 or you don’t.
        
                      
        
                      
          
                      Unique ID
                      Each token has a number that exists exactly once inside its contract.
                      
          
                      Indivisible
                      You transfer the whole token — there’s no “amount” field to split.
                      
          
                      One owner
                      The contract maps each token ID to a single address, enforced in code.
                      
          
                      Same machinery
                      It’s just a smart contract (ERC-721) — blocks, keys, gas and consensus, all from earlier modules.
                      
        
                      

        
                      What you actually own
                      
        
                      
          Here’s the part that surprises people: the artwork usually isn’t on the blockchain. Storing
          megabytes on-chain would cost a fortune in gas (Module 7), so an NFT typically stores only a tiny
          record — ownerOf[tokenId] plus a tokenURI, a link to a metadata file that
          points to the image. The chain proves who owns token #7; the picture it refers to lives
          somewhere else — often IPFS, sometimes an ordinary web server that can go down.
        
                      
        
                      
          Where that link points makes all the difference. A plain HTTPS URL is cheap but fragile: whoever
          runs the server can change the file or stop paying for it. An IPFS link uses content
          addressing — the address is a hash of the file (Module 2), so the content can’t be swapped without the
          address changing — but someone still has to keep a copy online (“pinning”). A fully on-chain
          NFT stores the artwork itself in the contract, usually as a compact SVG: it lives as long as the chain does, at a
          much higher gas cost.

                      Selling an NFT: approvals, marketplaces and royalties
                      
        
                      
          Marketplaces don’t take custody of your NFT. Instead you approve the marketplace’s contract as an
          operator — setApprovalForAll(market, true) — and when a buyer pays, the marketplace calls
          transferFrom on your behalf. That one approval covers every token you own in the collection,
          which is exactly why scam sites that trick people into signing it are the most common way NFTs are stolen.
        
                      
        
                      
          And the promised resale royalties (“the artist earns 5% of every future sale, forever”)? The
          ERC-721 standard has no such thing. A transfer is just ownerOf[id] = to; the contract never sees a
          price, so it can’t take a cut. Royalties were paid voluntarily by marketplaces — and when competition
          heated up in 2022–2023, several made them optional. (EIP-2981 only lets a contract advertise a royalty.)

                      Beyond profile-picture art
                      
        
                      
          Unique on-chain ownership turns out to be a general-purpose tool. The same ERC-721 record can represent
          far more than collectible pictures:
        
                      
        
                        
          
                      • Tickets & access — event tickets and memberships that can’t be counterfeited and resell with built-in rules.
                        • 
          
                      • Names & identity — human-readable addresses like alice.eth (ENS) are NFTs you own and can transfer.
                        • 
          
                      • In-game and virtual items — items a player owns independently of any one game’s servers.
                        • 
          
                      • Real-world assets & certificates — deeds, diplomas and provenance records, where a tamper-evident owner history is the whole point.
                        • 
        
                      

        
                      
          
                      Key takeaways
                      
          
                        
            
                      • An NFT is an entry in a contract’s ownerOf table: one unique ID, one owner, moved only by the owner or an approved operator.
                        • 
            
                      • The chain usually stores a link to the art, not the art — so durability depends on where that link points (HTTPS, IPFS or on-chain).
                        • 
            
                      • Marketplaces work through approvals, which cover your whole collection — the favourite target of scam sites.
                        • 
            
                      • A blockchain enforces what’s in the code and nothing more: royalties were a marketplace courtesy, not a protocol rule.

                      Go deeper
                      
        
                      
          The 2021 boom, the crash, and what stuck
          
                      
            NFTs went from niche to mania in 2021: collections like CryptoPunks and Bored Apes traded for hundreds
            of thousands of dollars, a single Beeple collage sold for $69M at Christie’s, and gas fees spiked as
            people raced to mint (the same congestion you metered in Module 7). By 2022–2023 speculative prices
            collapsed — most pictures-for-profit collections fell ~90%+ and many went to near-zero.
          
                      
          
                      
            What survived the speculation is the boring, useful core: a standard, neutral way to represent
            ownership of one specific thing on a public ledger. Ticketing, blockchain domain names, in-game
            assets and tokenized real-world items keep using ERC-721 long after the profile-picture frenzy cooled —
            the technology outlasting the bubble around it.
          
                      
        
                      
        
                      
          Standards: ERC-721 vs ERC-1155
          
                      
            ERC-721 is the original one-token-one-owner standard you just used. ERC-1155
            (the “multi-token” standard) is a more flexible cousin: a single contract can manage many token
            types at once, each either non-fungible (a unique sword) or fungible in quantity (500 identical
            health potions). It was designed for games and large collections, where minting a separate contract per
            item would be wasteful, and it can transfer a whole batch of different tokens in one transaction.
          
                      
          
                      
            The throughline back to Module 7: all of these — ERC-20 currencies, ERC-721 NFTs, ERC-1155 multi-tokens
            — are just agreed-upon shapes for a contract’s storage and functions. “Standards” are how
            wallets and marketplaces know how to talk to a contract they’ve never seen before.

                      Module 9
                      
        
                      DeFi: exchanges and loans as open software
                      
        
                      
          Smart contracts can hold money and enforce rules — so exchanges and lending markets can run as public programs,
          with no company in the middle and no account to open. Here are the two building blocks behind most of
          decentralized finance, and the ways they get exploited.
        
                      

        
                      An exchange without an order book
                      
        
                      
          A traditional exchange matches buyers with sellers. An automated market maker (AMM) such as
          Uniswap replaces the order book with a pool holding two tokens and one rule: the product of the
          reserves, x · y = k, must never shrink. You trade against the pool — put USDC in, take ETH out — and
          the price is whatever keeps the product constant. Each trade also pays a 0.3% fee that stays in the pool.

            The pool holds 100 ETH and 300,000 USDC, so its price starts at 3,000 USDC per ETH. Small trades get roughly that
            price; big ones slide along the curve and pay more and more per ETH — price impact. Deeper pools
            mean less impact. And when a trade leaves the pool’s price off the wider market’s, arbitrage bots trade it back
            within seconds: that is how a pool with no idea what ETH “should” cost stays in line with the world.
          
                      
        
                      

        
                      The sandwich attack
                      
        
                      
          Your swap waits in the public mempool before it is mined (Module 6), and anyone can read it. A bot that sees a big
          buy can buy just before you — pushing the price up — let you buy at the worse price, then
          sell just after you at the higher price you created. You are the filling in its sandwich. The only
          defense in the transaction itself is your slippage tolerance: the worst price you agree to, beyond
          which your swap reverts.

            wallets now send swaps through private channels so bots never see them in the public mempool.
          
                        
        
                        

        
                        Providing liquidity: fees versus impermanent loss

          ratio and earn the 0.3% fees. The catch: when the price moves, arbitrageurs rebalance the pool — buying the token
          that’s rising from it — so LPs end up holding more of whatever fell. Compared with simply holding the two tokens,
          the LP position is worth less. That shortfall is impermanent loss: “impermanent” because it
          vanishes if the price returns to where it started, but very permanent if you withdraw before it does.

                        Borrowing without a bank
                        
        
                        
          Lending protocols such as Aave and Compound let anyone deposit crypto to earn interest, and anyone borrow against
          collateral — no credit check, no paperwork, because every loan must be over-collateralized. The
          protocol tracks a health factor: collateral value × a liquidation threshold ÷ debt. If prices
          move and it drops below 1, anyone may liquidate the loan: repay part of the debt and take that
          much collateral, plus a bonus, at a discount. No margin call, no grace period.

            at once. On “Black Thursday”, 12 March 2020, ETH fell by about half within a day; network congestion broke many

                        Key takeaways
                        
          
                          
            
                        • An AMM prices trades with a formula (x · y = k) instead of an order book; bigger trades suffer more price impact.
                          • 
            
                        • Public mempools invite sandwich attacks; slippage tolerance caps how much a bot can take from you.
                          • 
            
                        • Liquidity providers earn fees but suffer impermanent loss whenever the price moves.
                          • 
            
                        • DeFi loans are over-collateralized and liquidated automatically — by anyone, at a profit — when the health factor drops below 1.

          Flash loans: millions, with no collateral, for one transaction
          
                        
            Because a transaction either completes entirely or reverts entirely, a contract can lend you any amount with no
            collateral at all — as long as you pay it back within the same transaction. If you don’t, the whole
            thing reverts as if the loan never happened. Aave popularized these flash loans in 2020. They
            are great for arbitrage and for swapping collateral in one step — and they gave attackers instant
            whale-sized capital: in the bZx attacks of February 2020, borrowed millions pushed thin markets around to fool
            a protocol’s price oracle. Flash loans don’t create bugs; they remove the capital barrier to exploiting them.
          
                        
        
                        
        
                        
          Where does the yield come from?
          
                        
            Every DeFi return has to be paid by someone: traders paying swap fees, borrowers paying interest, or the protocol
            printing its own token as a reward (“emissions”) — which only pays off if someone later buys that token. The
            sustainable sources are the first two. A useful rule of thumb from the industry: if you can’t see where the
            yield comes from, you are the yield.
          
                        
        
                        
        
                        
          Concentrated liquidity: Uniswap v3
          
                        
            In the pool above, liquidity is spread across every price from zero to infinity, so most of it sits idle. Uniswap
            v3 (2021) let LPs concentrate their deposit on a price range they choose. Inside the range they earn far more fees
            per dollar; if the price leaves the range, their position turns entirely into the less valuable token and stops
            earning — impermanent loss, amplified. Liquidity provision became an active, professional strategy.
          
                        
        
                        
        
                        
          DeFi’s risk stack
          
                          
            
                        • Contract bugs — reentrancy (Module 7), rounding errors, missing access checks. Audits reduce, never remove, the risk.
                          • 
            
                        • Oracle manipulation — a protocol is only as honest as its price feed.
                          • 
            
                        • Admin keys and upgrades — many “decentralized” protocols can be changed or paused by a small team or multisig.
                          • 
            
                        • Bridges — contracts holding assets for other chains were the biggest targets of 2022: Ronin (~$625M), Wormhole (~$320M), Nomad (~$190M).
                          • 
            
                        • Stablecoin and collateral risk — when a stablecoin or a big collateral asset fails (Terra, 2022; Module 7), every protocol built on it inherits the loss.

                        Module 10
                        
        
                        Zero-knowledge proofs: proving without revealing
                        
        
                        
          Can you convince someone a statement is true without revealing why it is true? Zero-knowledge proofs say
          yes — and they now secure billions of dollars in ZK rollups and make private payments possible. Two hands-on
          protocols build the intuition.
        
                        

        
                        The paradox
                        
        
                        
          Prove you know a password without typing it. Prove you’re over 18 without showing your birth date. Prove a batch of
          10,000 transactions was processed correctly without anyone re-running them. A zero-knowledge proof
          (introduced by Goldwasser, Micali and Rackoff in 1985) must be:
        
                        
        
                        
          
                        Complete
                        If the statement is true, an honest prover can always convince the verifier.
                        
          
                        Sound
                        If it’s false, a cheating prover gets caught — except with a vanishingly small probability.
                        
          
                        Zero-knowledge
                        The verifier learns nothing except that the statement is true.
                        
        
                        

        
                        
          
                        Try it: the magic cave
                        
          
                        
            A ring-shaped cave has a magic door deep inside, opened only by a secret word. Peggy wants to prove to Victor she
            knows the word without saying it. She walks in along path A or B while Victor waits outside; then Victor shouts
            which path she must come back out of. With the word she can always obey — through the door if needed. Without it,
            she only succeeds if Victor happens to call the side she’s already on.
          
                        
          
                        
            
            
                        
              
                        
              
                        
                
                
                
              
                        
              
                        Round-by-round: Peggy picks a path at random, then Victor calls one.
                        
              
                          
            
                          
          
                          
          
                          
          
                          
            One round proves little — a bluffer survives half the time. But each round halves her chances: after 20 rounds a
            bluffer survives one time in a million. And here is the zero-knowledge part: Victor’s video of the rounds would
            convince nobody else, because Peggy and a friend could stage the same footage by agreeing on the calls in
            advance. Victor ends up certain, yet holding nothing he could pass on — he learned only that she knows.
          
                          
        
                          

        
                          A real protocol: proving a map can be 3-coloured
                          
        
                          
          The cave is a story; here is genuine computer science (Goldreich, Micali and Wigderson, 1986). Peggy knows how to
          colour every node of a graph with one of three colours so that no line joins two nodes of the same colour — hard to
          find, easy to check. She proves she knows such a colouring without revealing it. Each round: she
          shuffles the three colours, commits to each node’s colour with a hash
          (exactly the sealed envelopes of Module 2), Victor picks one line, and Peggy opens only its two
          envelopes. Two different colours? Pass. Because the colours are reshuffled every round, Victor never learns the
          actual colouring.
        
                          

        
                          
          
                          Try it: verify a zero-knowledge proof
                          
          
                          
            Peggy…

            You can also click a line in the picture. A bluffer has at least one bad line, so each round she survives with
            probability at most 11/12: after 25 rounds that’s ~11%, after 100 rounds 0.017%. The opened colours are freshly
            shuffled every round — compare rounds and you’ll see the same node “change colour”, so the transcript reveals
            nothing about the real colouring. And because the commitments are salted hashes, Peggy can’t change a node’s
            colour after seeing which line Victor picked.
          
                            
        
                            

        
                            From conversation to proof: Fiat–Shamir
                            
        
                            
          A blockchain can’t hold a live conversation with every verifier. The trick (Fiat and Shamir, 1986): let a hash
          function play Victor. Peggy commits, hashes her own commitments, and uses the hash output as the “random” challenge
          — she can’t predict it without committing first, so she can’t cheat any more than before. The whole exchange
          collapses into one message that anyone can check later. Add heavy mathematics to make proofs tiny and fast to
          verify, and you get the zk-SNARKs and zk-STARKs used on blockchains today.
        
                            

        
                            Where zero-knowledge proofs are used
                            
        
                              
          
                            • ZK rollups — prove that thousands of transactions were executed correctly; Ethereum checks one small proof instead of re-running them all (Module 7).
                              • 
          
                            • Private payments — Zcash (2016) hides sender, receiver and amount while proving no money was created out of thin air.
                              • 
          
                            • Identity — prove you are over 18, or a citizen, or on an allow-list, without revealing who you are.
                              • 
          
                            • Verifiable computation — outsource a heavy calculation and get a proof the answer is right, instead of trusting the server.
                              • 
        
                            

        
                            
          
                            Key takeaways
                            
          
                              
            
                            • A zero-knowledge proof is complete, sound and zero-knowledge: convincing if true, nearly impossible to fake, and revealing nothing else.
                              • 
            
                            • Repetition drives a cheater’s odds toward zero: each round multiplies her survival chance by a fraction.
                              • 
            
                            • Commitments (salted hashes) stop the prover changing answers; fresh randomness each round keeps the verifier from learning anything.
                              • 
            
                            • Fiat–Shamir replaces the verifier’s coin flips with a hash, turning interactive proofs into ones anyone can verify — the basis of ZK rollups.
                              • 
          
                            
        
                            

        
                            Go deeper
                            
        
                            
          SNARKs vs STARKs
          
                            
            zk-SNARKs (“succinct non-interactive arguments of knowledge”) produce proofs of a few hundred bytes
            that verify in milliseconds, but most constructions need a one-time trusted setup: secret randomness that
            must be destroyed afterwards, or whoever kept it could forge proofs. zk-STARKs (“scalable,
            transparent”) need no trusted setup and rely only on hash functions — which also makes them believed to resist
            quantum computers — at the cost of larger proofs (tens to hundreds of kilobytes). Rollups use both.
          
                            
        
                            
        
                            
          The ceremony: how Zcash handled its trusted setup
          
                            
            Before launching in 2016, Zcash generated its SNARK parameters in a “ceremony”: six participants in different
            places each contributed a piece of the secret randomness and then destroyed their machines’ copies. The setup is
            safe as long as at least one participant really destroyed their piece. Later ceremonies scaled the idea up
            — Ethereum’s 2023 KZG ceremony for rollup data drew over 140,000 contributions — so that trusting “at least one
            honest participant” is a very safe bet.
          
                            
        
                            
        
                            
          What “zero knowledge” means precisely
          
                            
            The formal definition is the cave’s video trick turned into mathematics: a protocol is zero-knowledge if a
            simulator — someone who does not know the secret — could produce transcripts that look
            exactly like real ones. In the graph protocol the simulator just picks the challenged line in advance and gives its
            two nodes different random colours. If fake transcripts are indistinguishable from real ones, a real transcript
            can’t contain any knowledge about the secret.

                            Glossary
                            
        
                            Quick definitions for the terms used across the course. One opens at a time.
                            

        
                            
          
          
        
                            
        
                            

        
                            
          
                            51% attack
                            Controlling a majority of mining power (PoW) or stake (PoS), enough to censor or reorder recent transactions. Prohibitively expensive on large networks.
                            
          
                            ABI & function selector
                            The ABI (application binary interface) is a contract’s published map of functions to their byte encoding. A call identifies the function by its selector — the first 4 bytes of the Keccak-256 hash of its signature — letting any wallet invoke a contract it has never seen, given the ABI.
                            
          
                            Address checksum
                            Error detection built into address formats — Base58Check, Bech32 and Ethereum’s mixed-case EIP-55 — so a mistyped address is rejected instead of paid.
                            
          
                            AMM (automated market maker)
                            A smart contract that trades two tokens from a pool using a formula — most famously x · y = k — instead of matching buyers with sellers.
                            
          
                            Approval (setApprovalForAll)
                            Permission for another address, such as a marketplace, to move your tokens. One approval covers a whole collection, which makes it the favourite target of phishing sites.
                            
          
                            Base fee & tip (EIP-1559)
                            Ethereum’s fee model since 2021: a protocol-set base fee that is burned — rising after blocks more than half full and falling after emptier ones, by at most 12.5% per block — plus an optional tip that pays the validator.
                            
          
                            Birthday bound
                            Collisions in an n-bit hash appear after roughly 2n/2 tries, because every new hash is compared with every earlier one. SHA-256 therefore has 128-bit collision security.
                            
          
                            Block
                            A batch of transactions plus metadata: the previous block’s hash, a nonce, and its own hash. The first block of a chain is the genesis block.
                            
          
                            Blockchain
                            A shared, append-only ledger replicated across many computers, where blocks of records are linked by hashes so history can’t be quietly rewritten.
                            
          
                            Blockchain trilemma
                            The rule of thumb that decentralization, security and scalability trade off against each other — base layers usually maximize the first two and reach for scale via layer 2.
                            
          
                            Bytecode & opcodes
                            Contracts are stored as bytecode: one-byte instructions (opcodes) such as PUSH1, ADD and SSTORE, each with a fixed gas cost, run by the EVM’s stack machine.
                            
          
                            Change output
                            A transaction output that returns leftover value to the sender. Leave it out and the whole remainder goes to the miner as a fee.
                            
          
                            Cold / hot wallet
                            Cold = keys kept on a device that never touches the internet (hardware wallet, steel plate); hot = keys on an online device. Convenience goes up, safety goes down.
                            
          
                            Commitment (commit–reveal)
                            Publishing the hash of a value plus a random salt to lock it in without revealing it. Binding: it can’t be changed later. Hiding: it can’t be guessed.
                            
          
                            Confirmation
                            Each block added after the one containing your transaction. More confirmations = deeper burial = harder to reverse.
                            
          
                            Content addressing / CID
                            Naming data by its hash, as IPFS does with content identifiers (CIDs): change the content and the address changes, so it can’t be swapped silently.
                            
          
                            DAO
                            Decentralized autonomous organization — members coordinate through tokens and on-chain votes, and the treasury is controlled by a smart contract instead of officers. (“The DAO”, 2016, was the first and most infamous one.)
                            
          
                            DeFi & NFT
                            Decentralized finance: lending, trading and earning interest via smart contracts. NFTs: unique on-chain tokens representing ownership of a specific item.
                            
          
                            Difficulty adjustment
                            The automatic re-tuning of the proof-of-work target (every 2,016 blocks on Bitcoin) so blocks keep arriving roughly every 10 minutes no matter how much hashpower joins or leaves.
                            
          
                            Digital signature
                            Proof, verifiable by anyone, that the holder of a private key approved one exact message. The basis of transaction authorization.
                            
          
                            Discrete logarithm problem
                            Recovering k from k × G. Computing forward takes a few hundred steps; no known method reverses it faster than brute force, which is what makes elliptic-curve keys safe.
                            
          
                            Double-spend
                            Trying to spend the same coin twice. Consensus guarantees at most one of the conflicting transactions is ever confirmed.
                            
          
                            Elliptic curve / secp256k1
                            The curve y² = x³ + 7 over a 256-bit prime field, used by Bitcoin and Ethereum. A public key is the private key times a fixed point G.
                            
          
                            ERC-20 / ERC-721 / ERC-1155
                            Standard “shapes” for Ethereum token contracts: ERC-20 for fungible currencies, ERC-721 for one-of-a-kind NFTs, and ERC-1155 for a mix of fungible and non-fungible tokens in a single contract.
                            
          
                            Ethereum / EVM
                            The largest smart-contract blockchain. Every node runs the Ethereum Virtual Machine (EVM), so contracts execute identically everywhere; ETH is its native coin and pays for gas.
                            
          
                            Fiat–Shamir
                            Replacing a verifier’s random challenges with a hash of the prover’s own commitments, which turns an interactive proof into a single message anyone can verify.
                            
          
                            Finality
                            The point after which a transaction can’t be reversed. Probabilistic under PoW (deeper = safer, never absolute); explicit under Ethereum PoS, where reverting a finalized block requires destroying at least ⅓ of all staked ETH.
                            
          
                            Flash loan
                            An uncollateralized loan that must be repaid within the same transaction; if it isn’t, the whole transaction reverts as if it never happened.
                            
          
                            Fork (soft / hard)
                            A change to the protocol rules. Soft forks tighten rules and stay backward-compatible; hard forks don’t — if part of the network refuses to upgrade, the chain splits in two (Bitcoin / Bitcoin Cash, Ethereum / Ethereum Classic).
                            
          
                            Fungible vs. non-fungible
                            Fungible tokens are interchangeable — any one unit equals any other (BTC, ETH, dollars). Non-fungible tokens (NFTs) are each unique and indivisible, identified by a token ID; you own a specific item, not an amount.
                            
          
                            Gas / fees
                            The price paid to have the network process your transaction or run your contract. Every EVM operation costs a fixed amount of gas; running out reverts the call but the gas is still paid.
                            
          
                            Gwei
                            A billionth of an ETH — the unit gas prices are quoted in. Your fee is gas used × gas price in gwei.
                            
          
                            Halving
                            Bitcoin’s block reward cuts in half every 210,000 blocks (~4 years): 50 → 25 → 12.5 → … BTC. It’s why total supply approaches, but never exceeds, 21 million coins.
                            
          
                            Hash
                            A fixed-size fingerprint of any data, produced by a one-way function such as SHA-256. Any change to the input produces a completely different hash.
                            
          
                            HD wallet & derivation path
                            A wallet (BIP-32) that derives a whole tree of keys from one seed, addressed by paths such as m/44'/60'/0'/0/0 (BIP-44) — the same words restore every account.
                            
          
                            Health factor & liquidation
                            In lending protocols: collateral value × liquidation threshold ÷ debt. Below 1, anyone may repay part of the loan and take collateral at a discount.
                            
          
                            Impermanent loss
                            How much less a liquidity position is worth than simply holding the same two tokens, after the price moves. It shrinks back to zero only if the price returns.
                            
          
                            Keccak-256
                            Ethereum’s hash function: the version of SHA-3 from before NIST changed its padding, so its outputs differ from the standard SHA3-256.
                            
          
                            Layer 2 / rollup
                            A network that executes transactions cheaply off the main chain, then posts compressed proof of them on-chain — inheriting its security at a fraction of the fee.
                            
          
                            Liquidity pool / LP
                            The two tokens deposited in an AMM by liquidity providers (LPs), who earn the trading fees in exchange for bearing impermanent loss.
                            
          
                            Mempool
                            Each node’s waiting room of valid but not-yet-confirmed transactions, from which miners/validators assemble blocks.
                            
          
                            Merkle proof (SPV)
                            The sibling hashes on the path from a transaction up to the Merkle root — about log₂(n) of them — which prove the transaction is in a block without downloading it.
                            
          
                            Merkle tree / root
                            A tree of hashes: transactions are hashed in pairs, then the pairs are hashed in pairs, up to a single Merkle root stored in the block header. Changing any transaction changes the root, and inclusion of one transaction can be proven with only ~log₂(n) hashes.
                            
          
                            MEV
                            Maximal extractable value — profit a block producer (or a bot bidding for position) can capture purely by choosing the order of transactions in a block, e.g. “sandwiching” a victim’s trade. Mitigated, not eliminated, by proposer–builder separation.
                            
          
                            Mining
                            Racing to find a valid nonce for the next block. The winner earns newly issued coins plus transaction fees.
                            
          
                            Mining pool
                            Miners who combine hashpower and split each block reward in proportion to work contributed — trading lottery-style jackpots for a steady trickle.
                            
          
                            Mint
                            Creating a new token on-chain. Minting an NFT writes a fresh, never-before-used token ID into the contract and assigns it an owner.
                            
          
                            Node
                            A computer that stores the ledger, validates new blocks and relays transactions. Anyone can run one.
                            
          
                            Nonce
                            “Number used once” — the value miners vary to search for a hash that satisfies the difficulty target.
                            
          
                            Oracle
                            A service that feeds off-chain facts (like prices) to smart contracts, which cannot fetch external data themselves. A trustless contract is only as honest as its oracle — the “oracle problem”.
                            
          
                            Over-collateralization
                            Borrowing less than your collateral is worth, so the collateral still covers the debt if prices fall — DeFi’s substitute for credit checks.
                            
          
                            Price impact & slippage tolerance
                            Price impact is how far your own trade moves an AMM’s price; your slippage tolerance is the worst price you will accept before the swap reverts.
                            
          
                            Private key
                            A secret number that controls an address’s funds. Whoever knows it owns the coins; lose it and the coins are gone forever.
                            
          
                            Proof of Stake (PoS)
                            Consensus by collateral: validators lock up coins for the right to propose blocks, and lose them (“slashing”) if they cheat.
                            
          
                            Proof of Work (PoW)
                            Consensus by computation: blocks are expensive to produce but cheap to verify, so rewriting history costs more than honest participation.
                            
          
                            Public key / address
                            The shareable half of a key pair. An address — what you give people to get paid — is essentially a hash of the public key.
                            
          
                            Reentrancy
                            A bug where a contract calls out to another before updating its own state, letting the callee call back in and repeat the action — how The DAO was drained in 2016. Fixed by “checks, effects, interactions”.
                            
          
                            Sandwich attack
                            An MEV strategy: buy just before a victim’s swap and sell just after it, profiting from the price move the victim’s trade causes.
                            
          
                            Satoshi / wei
                            The smallest units of the major coins: 1 BTC = 100,000,000 satoshis; 1 ETH = 10¹⁸ wei. On-chain amounts are integers of these units — the decimals are just display.
                            
          
                            Seed phrase
                            12 or 24 dictionary words (BIP-39) encoding a wallet’s master secret. An HD wallet re-derives every key from it, so anyone holding the words holds all the coins.
                            
          
                            SHA-256d
                            SHA-256 applied twice. Bitcoin uses it for block hashes and transaction IDs.
                            
          
                            Signing nonce (ECDSA k)
                            The one-time secret number mixed into every ECDSA signature. Reusing it for two messages reveals the private key; RFC 6979 derives it deterministically so it never repeats.
                            
          
                            Slashing
                            Destroying part or all of a misbehaving proof-of-stake validator’s stake and ejecting it, for provable offences such as signing two conflicting blocks.
                            
          
                            Smart contract
                            A program stored on-chain that runs exactly as written when triggered by a transaction — the engine behind tokens, DeFi and NFTs.
                            
          
                            Stablecoin
                            A token engineered to track a currency like the US dollar — via custodial reserves (USDC, USDT), overcollateralized crypto (DAI), or — riskily, see Terra 2022 — pure algorithms.
                            
          
                            Sybil attack
                            Creating many fake identities to gain influence. It is why blockchains weight votes by something costly — work or stake — rather than counting computers.
                            
          
                            Target & bits
                            The number a block’s hash must be at or below. The header stores it in a compact 4-byte “bits” field; difficulty is the genesis target divided by the current one.
                            
          
                            Token URI / metadata
                            The link an NFT stores pointing to its metadata (name, traits and image). The artwork itself usually lives off-chain — on IPFS or a web server — so the chain records ownership, not the picture.
                            
          
                            Token vs. coin
                            A coin is a blockchain’s native currency (BTC, ETH). A token is an asset created by a smart contract on top of an existing chain.
                            
          
                            UTXO
                            Unspent transaction output — Bitcoin’s version of a coin, behaving like a bill: transactions consume whole UTXOs and create new ones, including “change” back to the sender. Ethereum uses account balances instead.
                            
          
                            Wallet
                            Software or hardware that stores keys and signs transactions. It holds no coins — coins exist only as ledger entries.
                            
          
                            Zero-knowledge proof
                            A proof that a statement is true which reveals nothing else. It must be complete (truths convince), sound (falsehoods get caught) and zero-knowledge.
                            
          
                            zk-SNARK / zk-STARK
                            Compact, non-interactive zero-knowledge proofs. SNARKs are tiny and fast to check but usually need a trusted setup; STARKs need none and rely only on hash functions.
